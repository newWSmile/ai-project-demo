# Spring AI 与 Java 原生 HttpClient 对比实验

## 实验目的

在相同模型、系统提示词、用户问题和 temperature 下，对比 Spring AI `ChatClient` 与 Java 21 原生 `HttpClient` 调用 DashScope 的 Token 和端到端耗时。

## 控制变量

- 模型：`qwen-plus`
- temperature：`0.2`
- 系统提示词：使用 `PromptConstants.DEFAULT_SYSTEM_PROMPT`
- 用户问题：`请用三句话解释什么是大语言模型`
- 调用方式：非流式
- 每种实现连续调用 3 次

## 原始数据

| 实现 | 次数 | 输入 Token | 输出 Token | 总 Token | 耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Spring AI | 1 | 48 | 80 | 128 | 2666ms |
| Spring AI | 2 | 48 | 79 | 127 | 1800ms |
| Spring AI | 3 | 48 | 80 | 128 | 1678ms |
| 原生 HttpClient | 1 | 48 | 79 | 127 | 1952ms |
| 原生 HttpClient | 2 | 48 | 86 | 134 | 2303ms |
| 原生 HttpClient | 3 | 48 | 79 | 127 | 1978ms |

## 汇总结果

| 指标 | Spring AI | 原生 HttpClient |
| --- | ---: | ---: |
| 平均输入 Token | 48 | 48 |
| 平均输出 Token | 79.67 | 81.33 |
| 平均总 Token | 127.67 | 129.33 |
| 平均耗时 | 2048ms | 2077.67ms |
| 中位数耗时 | 1800ms | 1978ms |

原生 HttpClient 的平均耗时比 Spring AI 高约 `29.67ms`，约为 `1.45%`。样本只有 3 次，且模型输出长度和网络状态存在波动，因此该差异不能证明两种实现存在稳定的性能差距。

## 观察与结论

1. 两种实现的输入 Token 始终为 `48`，说明模型接收到的提示词内容在 Token 层面等价。
2. 输出 Token 在 `79～86` 之间波动，属于模型生成的不确定性；第二次原生调用生成内容更长，耗时也相对更高。
3. 两种实现的端到端耗时处于同一量级，主要时间消耗来自网络传输和模型推理，当前实验中看不出 Spring AI 封装造成明显性能损失。
4. 3 次样本只能用于学习和初步观察，不能作为严谨的性能基准测试结果。

## 工程选择

| 维度 | Spring AI | 原生 HttpClient |
| --- | --- | --- |
| 代码量 | 少 | 多 |
| 协议细节 | 框架封装 | 完全可见、可控制 |
| 流式调用 | API 简洁 | 需要自行解析 SSE 数据帧 |
| 重试 | 已配置 Spring AI Retry | 需要自行实现 |
| 供应商切换 | 抽象程度较高 | 需要修改请求和响应模型 |
| 异常处理 | 框架提供基础封装 | 状态码、网络异常和解析异常全部自行处理 |
| 适合场景 | 企业应用主调用链 | 协议学习、特殊兼容和底层问题排查 |

当前项目的推荐方案是：主业务使用 Spring AI，保留原生 HttpClient 实验代码作为协议学习、问题定位和特殊供应商兼容的参考实现。
