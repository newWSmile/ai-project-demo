# 模型供应商适配层与对话记忆

## 一、核心结论

1. 业务系统应使用自己的模型请求和响应对象，不能让业务代码直接依赖某个供应商的 DTO。
2. 每个模型供应商由独立适配器负责协议转换、鉴权、错误映射和响应解析。
3. OpenAI-compatible Chat API 通常是无状态的；模型能使用的是本次请求携带的上下文，不会自动拥有跨请求记忆。
4. 对话记忆由应用负责存储、筛选、压缩和重新组装，再通过 `messages` 发送给模型。
5. 原始历史、滚动摘要、近期消息和结构化长期事实需要分层管理，不能只依赖一份会不断丢失细节的摘要。

## 二、为什么要定义自己的 Request 和 Response

业务层直接使用 DashScope、OpenAI 或其他供应商的请求对象，会导致供应商字段扩散到 Controller、Service 和业务逻辑中。更换模型时，大量业务代码都可能被迫修改。

推荐的依赖方向是：

```text
Controller / Business Service
            ↓
      ModelGateway 接口
            ↓
  项目自己的 ModelRequest / ModelResponse
            ↓
       Provider Adapter
            ↓
供应商 DTO、HTTP 协议、SDK 和鉴权方式
```

项目内部可以定义稳定的领域模型：

```java
/** 模型调用入口，业务层只依赖该接口，不感知具体供应商。 */
public interface ModelGateway {
    ModelResponse chat(ModelRequest request);
}

/** 项目内部的模型请求，只表达业务真正需要的通用能力。 */
public record ModelRequest(
        List<ModelMessage> messages,
        Double temperature,
        Integer maxOutputTokens
) {
}

/** 项目内部的统一响应，屏蔽供应商返回字段差异。 */
public record ModelResponse(
        String content,
        TokenUsage usage,
        String finishReason
) {
}
```

供应商适配器负责：

- 将 `ModelRequest` 转换为供应商请求 DTO；
- 添加 API Key、签名和供应商特有 Header；
- 处理普通响应、SSE 数据帧和结束标记；
- 将 401、429、5xx 和供应商业务错误转换为项目异常；
- 将供应商 Usage、finish reason 和消息内容转换为统一响应；
- 实现供应商所需的超时、重试和兼容逻辑。

这样切换供应商时，通常只需要新增或替换 Adapter，不需要修改业务调用层。

### 不要过度抽象

不同供应商即使都声称兼容 OpenAI 协议，在工具调用、多模态内容、流式事件、Usage、错误码和参数支持上仍可能存在差异。统一接口应只抽象项目真正使用的公共能力；供应商特有功能可以通过扩展参数或能力接口表达，不能为了“绝对统一”隐藏重要差异。

## 三、messages、上下文与记忆

`messages` 是一个有顺序的消息列表，常见角色包括：

- `system`：定义模型身份、行为边界和输出规则；
- `user`：用户提出的问题或提供的信息；
- `assistant`：模型此前给出的回答；
- `tool`：应用执行工具后返回给模型的真实结果。

多轮上下文示例：

```text
system: 你是一名准确的 AI 助手。
user: 我叫张三。
assistant: 你好，张三。
user: 我叫什么名字？
```

如果下一次请求只发送最后一句“我叫什么名字”，模型就无法可靠知道用户叫张三。

### 上下文不等于记忆

- 上下文：本次请求真正发送给模型的内容。
- 记忆：应用保存在数据库、Redis、对象存储或向量库中的历史信息。
- 记忆召回：应用从存储中选出与当前问题相关的信息，重新加入本次上下文。

模型只能看到上下文。所谓“模型记住了”，通常是应用在请求前完成了存储、召回和上下文组装。

## 四、企业级记忆分层

### 1. 原始消息历史

完整保存用户消息、模型回答、工具输入输出、时间和会话标识，用于审计、问题排查以及重新生成摘要。摘要不能替代原始记录。

### 2. 近期对话窗口

保留最近若干轮原始消息，避免摘要丢失当前话题的细节和语气。窗口大小应根据 Token 预算动态决定，而不是只按固定消息条数截取。

### 3. 滚动摘要

较早消息超过预算后，将其压缩成结构化摘要。摘要至少应包含：

- 已确认事实；
- 用户目标和限制条件；
- 已作出的决定；
- 尚未解决的问题；
- 关键编号、时间、金额和实体；
- 摘要覆盖的消息范围和版本。

摘要生成可能遗漏或误写信息，因此必须保留原始消息，并允许重新生成。

### 4. 结构化长期事实

姓名、偏好、组织、权限、长期目标等稳定事实应独立保存，并记录来源、更新时间和可信度。不能把所有长期记忆都埋在自然语言摘要中。

### 5. 检索型记忆

历史内容很多时，根据当前问题检索相关片段，而不是把全部历史发送给模型。检索结果只是候选上下文，还要进行权限、时效性和相关性过滤。

## 五、一次请求的上下文组装

推荐结构：

```text
本次 messages =
    系统提示词
  + 当前用户可用的结构化长期事实
  + 较早对话的滚动摘要
  + 与当前问题相关的历史召回内容
  + 最近若干轮原始消息
  + 当前用户问题
```

Token 预算必须满足：

```text
系统提示词
+ 工具定义
+ 长期事实
+ 历史摘要
+ 检索片段
+ 近期消息
+ 当前问题
+ 预留输出 Token
≤ 模型上下文窗口
```

不能把输入塞满整个上下文窗口，否则模型没有足够空间生成答案。

Token 预算需要在每一轮请求前重新估算，并在请求后使用实际 Usage 校准。完整说明参见：[大模型 Token 预算管理](./token-budget.md)。

## 六、压缩触发与常见风险

可以在预计输入 Token 达到预算阈值时触发压缩，例如达到可用输入预算的 70%～80%。具体阈值需要结合模型窗口、输出预留量、工具定义长度和业务风险调整。

常见风险：

- 直接删除旧消息，导致关键约束丢失；
- 只保留摘要，导致编号、金额和时间被改写；
- 把模型生成的推测当作已确认用户事实；
- 多个请求同时更新同一会话，造成消息顺序错乱；
- 不做权限隔离，召回了其他用户或其他组织的记忆；
- 将敏感信息无限期保存，违反数据最小化原则；
- 摘要被提示词注入污染，后续每轮持续携带恶意指令。

## 七、当前 model-api-lab 的对应关系

| 当前代码 | 角色 |
| --- | --- |
| `ChatRequest` / `ChatResult` | 项目对外 API 的请求和响应 |
| `OpenAiCompatibleRequest` / `OpenAiCompatibleResponse` | 供应商协议 DTO |
| `DashScopeRawClient` | DashScope 原生 HTTP 适配实现 |
| `ChatClient` | Spring AI 提供的模型调用抽象 |
| `RawChatController` | 原生适配器的 HTTP 入口 |

当前实现仍有以下限制：

- 尚未抽取统一的 `ModelGateway` 接口；
- 每次只发送系统提示词和当前用户问题；
- 没有 conversationId 和消息持久化；
- 没有近期窗口、摘要、长期事实和检索型记忆；
- 原生 HttpClient 尚未实现 SSE 流式解析和重试。

## 八、建议学习顺序

1. 手动构造多轮 `messages`，验证 API 本身无状态。
2. 抽取项目内部 `ModelRequest`、`ModelResponse` 和 `ModelGateway`。
3. 让 Spring AI 和 DashScope 原生客户端分别实现统一接口。
4. 增加 conversationId 和内存版消息存储，理解会话组装流程。
5. 再引入数据库持久化、Token 预算、近期窗口和滚动摘要。
6. 最后增加结构化长期事实、检索型记忆、权限与并发控制。
