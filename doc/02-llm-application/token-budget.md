# 大模型 Token 预算管理

## 一、核心结论

1. 每次调用模型前都应重新估算 Token 预算，不能只在会话创建时计算一次。
2. 请求前的 Token 数通常是估算值；请求后的供应商 Usage 是实际值，应记录并用于校准估算方法。
3. Token 预算不只是防止超过上下文窗口，还用于控制输出空间、调用成本、响应时间和用户配额。
4. 对话越长，应用越需要主动选择、压缩和舍弃上下文，不能把全部历史无限追加到 `messages`。

## 二、为什么每一轮都要重新估算

每轮请求都可能发生变化：

- 系统提示词升级；
- 当前用户问题长度不同；
- 历史消息持续增加；
- 滚动摘要被更新；
- RAG 检索片段数量和长度变化；
- 工具定义及 JSON Schema 发生变化；
- 不同模型的上下文窗口和 Tokenizer 不同；
- 本轮期望输出长度不同；
- 图片、音频等多模态输入引入额外 Token。

因此 Token 预算属于“每次请求的前置检查”，而不是会话级的一次性配置。

## 三、基本预算公式

一次模型请求需要满足：

```text
固定提示词 Token
+ 工具定义 Token
+ 长期事实 Token
+ 历史摘要 Token
+ 检索内容 Token
+ 近期消息 Token
+ 当前用户输入 Token
+ 预留输出 Token
+ 安全余量
≤ 模型上下文窗口
```

可以进一步计算本轮允许使用的历史上下文预算：

```text
历史上下文可用预算 =
    模型上下文窗口
  - 固定提示词
  - 工具定义
  - 当前用户输入
  - 预留输出
  - 安全余量
```

如果结果小于零，说明即使不携带历史，本轮请求也无法安全发送，应缩短当前输入、减少工具定义、降低输出上限或切换更大上下文模型。

## 四、为什么必须预留输出 Token

上下文窗口通常由输入和输出共同占用。如果输入已经占满窗口，模型就没有空间生成完整答案。

例如：

```text
模型上下文窗口：32,000
系统提示词和工具：3,000
当前用户输入：500
预留模型输出：2,000
安全余量：1,000

历史、摘要和检索内容最多可用：
32,000 - 3,000 - 500 - 2,000 - 1,000 = 25,500 Token
```

预留输出量应根据任务类型设置：

- 分类、判断、字段提取：较小；
- 普通问答：中等；
- 长报告、代码生成：较大；
- 工具调用：还要考虑工具结果返回后的下一轮模型调用。

## 五、请求前预算流程

### 第 1 步：读取模型能力

根据本轮选择的模型获取：

- 最大上下文窗口；
- 最大输出 Token；
- 对应 Tokenizer 或估算策略；
- 是否支持工具、多模态和流式 Usage。

这些能力应由模型配置管理，不能散落在业务代码中。

### 第 2 步：计算不可舍弃内容

优先计算：

- 系统提示词；
- 安全规则；
- 当前用户输入；
- 本轮必需的工具 Schema；
- 预留输出和安全余量。

这些内容已经超限时，不能通过删除历史来解决全部问题。

### 第 3 步：计算可用历史预算

从总窗口扣除不可舍弃内容，得到摘要、近期对话、长期事实和检索片段可以共同使用的预算。

### 第 4 步：按优先级组装上下文

推荐优先级需要结合业务调整，一般包括：

1. 与当前请求直接相关的安全规则和权限信息；
2. 当前任务必须使用的已确认事实；
3. 最近几轮原始对话；
4. 高相关检索片段；
5. 较早对话的滚动摘要；
6. 低相关历史信息。

低优先级内容先被缩短或移除，不能简单从消息列表头部机械截断。

### 第 5 步：超限处理

当预计 Token 超限时，可以依次采取：

1. 删除低相关或重复检索片段；
2. 缩短工具说明和冗余 Prompt；
3. 将较早原始消息压缩为滚动摘要；
4. 只保留最近若干轮原始消息；
5. 降低本轮最大输出 Token；
6. 切换更大上下文模型；
7. 如果核心输入仍然超限，明确拒绝并提示用户拆分任务。

## 六、请求后校准

模型返回后应记录：

- 估算输入 Token；
- 实际 `promptTokens`；
- 估算误差和误差比例；
- 实际 `completionTokens`；
- 模型名称与 Prompt 版本；
- 是否发生摘要、截断或内容舍弃；
- 总耗时、首 Token 耗时和费用。

校准公式示例：

```text
估算误差率 = |实际输入 Token - 估算输入 Token| / 实际输入 Token
```

如果某个模型的误差长期偏大，应更新它的 Tokenizer、协议开销或安全余量，不能简单扩大所有模型的统一余量。

## 七、如何估算 Token

### 精确 Tokenizer

优先使用与目标模型一致的官方 Tokenizer。不同模型的分词规则可能不同，同一段中文在不同模型中的 Token 数不一定相同。

### 近似估算

没有官方 Tokenizer 时，可以根据历史 Usage 建立保守估算，但只能作为降级方案。不能长期使用“一个汉字等于一个 Token”或固定字符比例，因为代码、中文、英文、JSON 和特殊符号的分词差异很大。

### 协议额外开销

估算不能只统计可见文本，还要考虑：

- 每条消息的 role 和消息边界；
- 工具名称、描述和 JSON Schema；
- 结构化输出 Schema；
- 图片或其他多模态输入；
- 供应商协议可能添加的内部格式开销。

请求后的实际 Usage 才是计费和监控的主要依据。

## 八、上下文预算、费用预算与用户配额

三者不能混为一谈：

- 上下文预算：防止超过模型窗口并保证输出空间；
- 费用预算：根据模型输入、输出单价控制本次或周期成本；
- 用户配额：限制某个用户、租户或 API Key 在一定周期内的调用量。

即使请求没有超过上下文窗口，也可能因为成本或用户配额而被拒绝。

## 九、建议的 Java 组件划分

```text
ModelCapabilities
    保存模型窗口、输出上限和能力信息

TokenCounter
    根据模型估算消息、工具和 Schema Token

TokenBudgetPolicy
    计算输出预留、安全余量和可用历史预算

ContextAssembler
    按优先级选择摘要、近期消息、事实和检索内容

ConversationCompressor
    在达到阈值时生成或更新滚动摘要

UsageRecorder
    记录估算值、实际 Usage、费用和误差
```

业务 Service 不应自行拼接所有历史并计算 Token，而应调用统一的上下文组装与预算组件。

## 十、常见错误

- 只在会话开始时计算一次预算；
- 只计算用户文本，忽略系统提示词和工具 Schema；
- 没有为输出预留空间；
- 达到限制后直接删除最早消息，导致关键约束丢失；
- 摘要持续增长却从不再次压缩；
- 使用某个模型的 Tokenizer 估算所有模型；
- 将字符数直接当作 Token 数；
- 只记录实际 Usage，不记录估算值，无法评估预算策略；
- 流式响应中拿不到 Usage 时，将其错误记录为零；
- 并发请求基于不同历史快照更新同一会话，导致预算和消息顺序错误。

## 十一、当前 model-api-lab 的状态

当前项目已经记录模型返回的实际 Usage，但尚未实现请求前 Token 估算和预算控制。

后续实现顺序建议：

1. 为模型建立 `ModelCapabilities` 配置；
2. 定义 `TokenCounter` 接口，允许不同模型使用不同实现；
3. 在请求前计算输出预留和可用输入预算；
4. 先实现近期窗口裁剪，再实现滚动摘要；
5. 记录估算值与实际 Usage 的误差；
6. 最后增加费用预算和用户级配额。
